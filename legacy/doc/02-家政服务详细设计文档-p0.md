# 02 家政服务详细设计文档（P0）

## 1. 文档信息

- 项目名称：家政服务平台
- 基础项目：`homemaking`
- 文档类型：P0阶段详细设计文档
- 当前版本：V1.0
- 适用对象：产品、后端、前端、小程序、测试、实施

## 1.1 文档范围说明

- 本文档作为 `P0` 阶段的正式详细设计基线，直接服务于当前阶段研发、联调、测试与实施
- 文档中涉及 `P1/P2` 的内容仅用于架构预留、字段预留、接口扩展预留，不作为当前阶段必须实现范围
- 当前阶段如需新增或调整设计，优先以本文件为准，不再回退到全阶段泛化表述
- 后续进入 `P1` 时，应在本文件基础上新增或演进对应阶段设计稿，不混淆 `P0` 已确认结论

## 2. 设计目标

- 在现有后台管理系统基础上，新增家政服务业务能力
- 支持后台管理端、小程序端、家政门户网站三端协同
- 保持后台权限体系稳定，不破坏现有 `sys_*` 系统模块
- 建立独立的家政业务域模型，支持后续持续扩展

## 3. 关键设计结论

### 3.1 账号体系结论

- `sys_user`：作为平台内部统一用户主表
- `hm_customer_user`：作为小程序 C 端用户资料表
- `hm_user_auth`：作为多登录方式绑定表

结论说明：

- 现阶段不单独建设独立鉴权中心
- 平台内部用户继续复用 `sys_user`
- 服务人员属于平台内部用户的一部分
- 小程序用户不进入后台权限体系
- 多登录方式通过绑定表扩展，不要求一次性全部实现

### 3.2 系统形态结论

- 后端：继续使用当前 Spring Boot 单体多模块架构
- 后台管理端：继续使用现有 `hm-ui`
- 小程序端：新增独立项目
- 门户网站：新增独立项目

### 3.3 业务域结论

建议新业务统一使用 `hm_` 前缀表与 `homemaking` 业务包，避免与 `sys_*` 混杂。

### 3.4 加盟结论

- 本期虽不一定立即实现加盟业务闭环，但数据库与权限模型需预留加盟组织能力
- 直营服务人员属于平台内部用户
- 非直营服务人员按加盟主体归属处理

## 4. 总体架构设计

```text

        |
        v

        |
        v
MySQL + Redis + 对象存储 + 微信能力
```

## 5. 三端设计

## 5.1 后台管理端

面向内部运营人员，主要职责：

- 服务配置
- 订单运营
- 人员管理
- 内容管理
- 数据统计

## 5.2 小程序端

面向 C 端消费者，主要职责：

- 浏览服务
- 预约下单
- 查看订单
- 评价与售后
- 当前 P0 不包含正式微信支付接入，支付相关内容仅保留设计与数据结构预留
- 当前 P0 登录主流程为首次微信授权登录并获取微信手机号
- 当前 P0 预留手机号验证码登录入口，但不纳入本轮实现
- 当前 P0 需支持“未绑定微信提醒弹框”，用户可关闭，但未绑定时下次登录继续提醒

### 5.2.1 小程序页面设计原则

- 页面优先保证下单转化效率
- 结构尽量清晰，不堆叠后台式复杂信息
- 核心动作突出：
  - 选择服务
  - 选择时间
  - 选择地址
  - 立即预约/提交订单
- 价格、服务说明、预约说明需清晰可见
- 状态页需完整覆盖：
  - 空列表
  - 加载中
  - 支付成功
  - 支付失败
  - 无可预约时间

### 5.2.3 小程序统一视觉基线

#### 视觉方向

- 关键词：可信、专业、温和、生活服务感、预约效率高
- 页面气质：家庭服务平台，不做强促销电商风
- 背景：浅色底，弱卡片层级
- 情绪：温暖但不花哨

#### 色彩建议

- 主色：暖橙色
  - 用途：主按钮、核心强调、价格重点
- 辅色：米白色/浅灰色
  - 用途：页面背景、卡片背景区分
- 功能色：
  - 成功：绿色
  - 警告：橙黄色
  - 失败：红色
  - 信息：浅蓝灰

#### 字体层级

- 页面标题：突出、稳重
- 模块标题：清晰，略强于正文
- 正文：易读，避免过小
- 辅助说明：灰度弱化
- 价格：使用主色强调，字号高于正文

#### 组件统一规范

- 主按钮：整行固定宽按钮，圆角明显
- 次按钮：描边或浅底
- 卡片：圆角卡片，弱阴影或纯描边
- 状态标签：统一尺寸、统一圆角、统一颜色语义
- 表单项：标题在上，输入区域清晰，点击区域充足
- 列表卡片：统一封面比例、标题层级、价格展示结构

#### 间距规范

- 页面左右边距统一
- 模块间距统一
- 卡片内上下间距统一
- 表单项之间间距统一

#### 导航规范

- 顶部导航标题简洁
- 页面回退逻辑明确
- 底部主操作区固定在需要转化的页面上

### 5.2.4 小程序页面详细设计

#### 5.2.4.1 登录授权页

页面目标：

- 完成用户首次进入小程序时的身份确认
- 获取微信授权并引导进入首页
- 首次登录获取微信手机号，作为预约联系方式默认来源
- 为手机号验证码登录预留后续扩展入口

页面结构：

- 顶部品牌区
  - Logo
  - 品牌名
  - 一句信任型说明文案
- 中部权益说明区
  - 可查看服务
  - 可在线预约
  - 可查看订单
- 底部操作区
  - 微信授权登录主按钮
  - 微信手机号授权说明
  - 手机号验证码登录入口预留
  - 用户协议与隐私政策勾选提示

关键交互：

- 未勾选协议时按钮点击给出提示
- 授权成功进入首页
- 已登录用户自动跳过
- 若当前账号未绑定微信，登录后弹出绑定提醒
- 绑定提醒允许关闭，但关闭后不改变未绑定状态，下次登录继续提醒

状态设计：

- 授权失败提示
- 网络异常提示

#### 5.2.4.2 首页

页面目标：

- 承接流量入口
- 快速引导用户进入服务浏览与预约

页面结构：

- 顶部定位与搜索区
  - 当前服务城市/区域
  - 搜索入口
- Banner 区
  - 支持轮播

- 快捷服务价格标签区
- 快捷服务宫格区

  - 服务卡片列表

- 点击服务人员进入服务人员展示或关联服务

状态设计：

补充规则：

- 手机号验证码登录先预留设计

### 多登录方式对象

- 数据来源：`hm_user_auth`
- 作用：建立用户与登录方式之间的绑定关系

## 8. 业务流程设计

## 8.1 小程序下单流程

```text
小程序首页
-> 服务列表
-> 服务详情
-> 选择地址
-> 选择预约时间
-> 选择规格/附加项
-> 提交订单
-> 创建待支付订单
-> 拉起微信支付
-> 支付成功
-> 进入待确认/待派单
-> 后台派单
-> 服务上门
-> 服务完成
-> 用户评价
```

## 8.2 后台派单流程

```text
后台查看待派单订单
-> 筛选符合条件服务人员
-> 派单
-> 服务人员接单
-> 到达上门
-> 开始服务
-> 完成服务
-> 订单完成
```

## 8.3 门户留资流程

```text
门户访客浏览
-> 提交咨询表单
-> 后台生成线索
-> 客服跟进
-> 转化下单或沉淀客户
```

## 8.4 后台微信扫码登录流程

```text
用户发起微信扫码
-> 获取微信身份信息
-> 查询 hm_user_auth 是否已绑定平台用户
-> 若已绑定则登录成功
-> 若未绑定则尝试根据手机号匹配既有 sys_user
-> 匹配成功后完成绑定并登录
-> 匹配失败则拒绝登录
```

规则说明：

- 扫码登录不是注册方式
- 没有命中既有平台用户则不能登录

## 8.5 加盟模型流程说明

```text
平台直营用户 -> 归属平台组织
加盟商用户 -> 归属加盟组织
订单/人员/商品/区域 -> 按组织归属管理
```

## 13. 对现有系统的改造点

- 新增小程序登录认证逻辑
- 新增平台扫码登录绑定逻辑
- 新增门户匿名接口
- 新增后台菜单与权限
- 新增加盟组织能力

## 13.2 前端后台改造点

- 新增“家政业务”菜单
- 新增服务、人员、订单、内容、小程序运营、加盟管理等页面
- 复用现有列表、表单、字典、上传组件

## 13.3 小程序新增能力

- 独立前端工程
- 调用 `/api/mini/**`
- 微信登录、地址、下单、评价
- 首页导航与首页运营配置动态读取
- 按详细设计文档中的 P0 页面清单实施
- 微信支付从当前开发范围移出，保留后续扩展能力
- 微信小程序登录所需 `appId`、`appSecret` 由后端环境配置管理，不放入小程序前端代码

## 13.4 门户网站新增能力

- 独立前端工程
- 调用 `/api/portal/**`
- 展示服务与内容
- 提交咨询线索
- 基础内容发布后自动读取最新发布内容

## 14. 非功能设计

### 14.1 安全

- 后台接口沿用现有 JWT 鉴权
- 小程序 token 与后台 token 分开
- 门户提交接口做限流、防刷、防重复提交
- 后台扫码登录必须命中既有平台用户

### 14.2 性能

- 首页和服务列表可做 Redis 缓存
- 内容页可做静态化或缓存
- 订单和派单相关接口以数据库实时为主

### 14.3 审计

- 后台关键操作接入现有操作日志
- 订单状态变更额外写入 `hm_order_operate_log`

### 14.4 扩展性

- 价格规则先保留简化版
- 时间段规则先 JSON 化
- 复杂计价后续再拆规则明细表
- 手机验证码登录本期可不开发，但表结构与接口需预留
- 微信支付本期不开发，但订单支付状态、支付渠道、支付回调扩展点需预留
- 微信绑定关系需在用户认证关系中预留扩展能力
- 公众号通知、小程序订阅消息、任务通知列入下一阶段预留
- 加盟组织维度在一期设计中预留

## 15. 实施顺序建议

### 第一阶段

- 数据库建表
- 后端基础实体与接口
- 后台服务类目、商品、人员、订单页面

### 第二阶段

- 小程序登录、首页、列表、详情、下单、订单

### 第三阶段

- 门户内容与留资

### 第四阶段

- 评价、退款、统计、营销

## 15.5 SQL落地要求

- 家政业务相关建表 SQL 统一并入现有 `sql/ry_20260330.sql`
- 新增业务表全部使用 `hm_` 前缀
- 文档口径按新项目描述，不再沿用旧开源项目命名表达

## 16. 研发注意事项

- 平台内部用户统一使用 `sys_user`
- 小程序用户单独使用 `hm_customer_user`
- 服务人员不是独立账户体系，而是平台内部用户的一部分
- 下单金额必须落库固化，不能实时重算覆盖历史订单
- 服务人员与订单关系必须保留派单历史
- 订单状态流转必须统一封装，不能散落在 Controller
- 评价必须绑定订单，防止脏数据
- 小程序菜单与首页配置不要复用后台权限菜单
- 加盟相关关键数据必须带组织归属

## 17. 文档结论

本设计方案以当前项目现有后台能力为平台底座，采用以下最终模型：

- `sys_user` 作为平台内部统一用户主表
- 服务人员属于平台内部用户的一部分
- `hm_customer_user` 作为小程序 C 端用户
- `hm_user_auth` 作为多登录方式绑定表
- `hm_org` 作为直营/加盟组织主体
- 小程序菜单与首页采用业务配置方式管理
- 门户采用后台内容发布驱动

该方案兼顾当前项目可落地性、后续多登录方式扩展以及加盟扩展能力，适合作为正式研发设计基线。
