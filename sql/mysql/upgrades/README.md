# 数据库初始化与增量升级

全新部署只需导入一次 [`../hm-init.sql`](../hm-init.sql)，它是独立 SQL 文件，不依赖客户端的 SOURCE 命令，已包含截至 V012 的全部初始化和升级步骤。导入后无需再执行 V002–V012。此目录中的编号脚本用于已有数据库升级。

维护数据库结构时，保留已发布的增量脚本，按顺序添加下一版本，然后运行 `node tools/migration/build-init.cjs` 更新单文件安装包。发布前运行 `node tools/migration/build-init.cjs --check`，内容不同会报错退出；部署人员直接使用仓库内的 hm-init.sql，无需安装 Node 或执行生成工具。原始分段 SQL 是生成来源，不是首次部署的操作清单。

V002 添加技能、服务区域、日期班次、请假、账号绑定、履约照片元数据、订单履约/改期字段、官网草稿/发布、套餐配额、分佣及结算明细。V003 补充管理菜单。V002 为一次性 DDL，执行成功后登记 `hm_schema_upgrade.version='V002'`；V003 登记 V003。V004 新增人员角色范围、门店授权、授权审计以及细权限菜单；也是一次性 DDL。

执行前停止应用写入，完整备份数据库并验证恢复能力。使用有 DDL 权限的安装账号逐份执行，遇错停止，不使用 `mysql --force`。MySQL DDL 不能由一个外部事务整体回滚，部分失败后应恢复备份或核对已执行结构再处理；不能盲目重跑已执行的版本。运行账号只需 DML 权限。升级后查询 `SELECT version,applied_at FROM hm_schema_upgrade ORDER BY version;`，应包含 V002 至 V012，再启动新 JAR。

新预约的产能规则从本轮开始严格执行。升级不会猜测旧人员的技能、行政区和班次；管理员必须在排班页确认并录入。未录入的人员不出现在可预约产能中。已存在的订单和占位保留；旧归档人员配置需结合实际运营规则核对后录入。

新增运行变量 `HM_EVIDENCE_ROOT` 指向私有持久目录，例如 `/var/lib/hm/evidence`。目录由后端账号读写、不得暴露为静态目录。数据库保存照片元数据，图片保存在该目录；两者须一同备份与恢复。不需要重新配置数据库密码进 JAR。

回滚前先停止写入。新版本产生订单、照片或结算明细后，直接换回旧 JAR 会失去对应业务能力；应通过备份恢复或专门的数据兼容方案完成回滚。不要删除数据表来掩盖升级失败。

V004 不把旧 `homemaking:manage` 自动升级为全权限。升级后由已有超级管理员登录「家政运营 → 人员权限」，为其他后台账号重新分配模板及门店；服务人员还需保留/建立人员账号绑定。模板同时写入系统角色菜单并清理权限缓存。若手工修改系统角色菜单，后端仍以模板作为权限上限。所有账号重新登录后刷新菜单。生产升级不能跳过此授权步骤。

V005 新增租户支付模式（默认 OFFLINE）、订单支付方式/线上截止时间、不可覆盖的收支流水和收款权限。已有线上支付订单继续保留 pay_order_id；旧已付款且无线上支付编号的订单标记 LEGACY，不伪造人工收款凭证。原金额和结算记录保留。旧线下/历史单须人工对账，不能冒用新的收款/退款入口修改历史资金。V005 需与新 JAR、管理端和小程序一起发布；启用新流水后不能直接回退到不认识这些字段的旧订单逻辑。

升级后的模板默认授权：老板拥有支付设置与收退款，店长可确认收款，财务可确认收款/退款/冲正。V005 同步补充已存在模板角色的菜单；重新登录刷新菜单，手工收回的权限可在系统角色中继续收回。变更可通过人员权限重新应用模板。

V006 增加订单变更快照、待处理变更关联、区域费用快照和地址/改价权限。已上线数据库执行一次 V006；新空库继续只执行 hm-init.sql。V006 不猜测旧订单的区域费用，也不补造旧变更记录；跨区改地址缺少历史报价时须由有改价权限的人员确认总价。更新后同步发布后端、管理端及小程序，重新登录刷新新增权限。没有新增环境变量。

V007 将平台身份从租户编号/角色名中独立出来。已升级到 V006 的旧库仅执行 V007；全新空库仍只执行 hm-init.sql。V007 新建 system_platform_operator、system_platform_access_lock、system_platform_access_log，迁移之前已具备平台资格的有效账号并写迁移审计；普通总部员工不会被授权。兼容迁移中对旧租户编号 1 的判断只用于识别旧规则下的既有平台账号，运行时代码没有该身份判断。

V007 同时把原 package_id=0 的业务租户转为普通直营业务套餐，将 system_tenant_package.menu_ids 扩为 TEXT 以容纳完整菜单 JSON；平台结算受益人用类型 PLATFORM + beneficiary_id=0 表示，不映射业务租户。旧 hm_staff_scope 的 PLATFORM 模板转为 OWNER 标记，实际平台资格以独立表为准；被撤销平台资格后如需业务权限，应单独分配对应业务模板。

V008 完整化服务人员自助工作台。已升级到 V007 的旧库仅执行 V008；它扩展既有 `hm_worker_leave`，保存请假/休息的申请、审核、撤销、乐观锁和幂等信息，并新建 `hm_worker_leave_log` 保存操作人及状态变化。旧请假记录继续标记为已批准的管理员登记，未知历史时间与操作人保持为空，不补造审计。升级同时增加本人请假、本人收入和请假审批权限；发布后所有服务人员重新登录。没有新增环境变量。

V009 增加客户完工确认状态、服务人员提交时间、确认期限、确认方式及确认人，并把订单与预约状态字段扩到 32 字符。升级不改变历史已完成订单，也不补造历史确认记录。发布后，服务人员提交完工只进入待客户确认；客户确认或无进行中售后时到期自动确认，之后才生成结算。确认期限在品牌与渠道中配置，默认 48 小时；没有新增环境变量。

V010 把原退款申请扩展为补做、更换服务人员、重新上门、部分退款、全额退款和其他补偿，并新增售后处理时间线、补救预约及人员关联。升级会把历史售后保留为部分退款类型，并为每条历史记录写一条迁移日志，不修改原状态或金额。补救服务重新经过技能、区域、班次、请假和占位校验，并重新进入人员履约与客户完工确认；退款继续使用 V005 的原支付路线、收支流水和结算冲正。没有新增环境变量。

V011 完整化评价：增加服务评分、服务人员评分、标签、私有图片、商家回复、公开/隐藏、推荐状态和不可变操作日志。已有评价保留原内容与星级，两个细分评分均复制原星级并标记为已发布；不会自动公开或推荐。图片与履约凭证共用 `HM_EVIDENCE_ROOT` 私有目录和备份策略，不新增环境变量。升级时同步发布后端、管理端、门户和小程序，并让相关后台人员重新登录以刷新“评价回复”权限。

V012 增加独立加盟商与合同中心：加盟档案只关联 `system_tenant`，不把租户表当加盟档案；保存加盟区域、合同期限、保证金约定与不可变收付流水，并支持合同生效、续约、提前终止和到期处理。负责人手机号和结算账号使用既有 `HM_DATA_ENCRYPTION_KEY` 加密，列表只显示掩码；有结算资料权限的平台管理员填写用途后才能查看明文，查看动作写入审计。该密钥必须与数据库一起长期保存，丢失或更换会使已存敏感资料无法解密。升级后平台管理员重新登录以刷新“加盟与合同”菜单；普通租户角色不会获得该入口。

升级前停止写入并备份；升级后核对独立授权表中的原平台账号、用普通直营老板验证跨租户拒绝，再通过平台身份页完成后续授权。同步发布 JAR 与管理端并重新登录；无新增环境变量。不要直接回退到按 tenant 1 判平台的旧 JAR。需要回滚时停止写入、恢复升级前数据库备份和配套程序，并确认升级后新授权/撤销如何处理。
